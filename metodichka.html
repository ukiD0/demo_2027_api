2. Теория: API, HTTP и JSON простыми словами

2.1. Что такое API

Представь кафе. Ты сидишь за столиком, а еда готовится на кухне. Ты не можешь зайти на кухню и взять что хочешь сам — там чужая территория и свои правила. Зато есть официант: ты говоришь ему «принеси борщ», он идёт на кухню, кухня готовит, официант приносит тебе тарелку.

API (Application Programming Interface — «программный интерфейс приложения») — это такой официант для программ. Одна программа не лазит напрямую в базу другой программы. Она отправляет запрос — и получает ответ в понятном формате.

В модуле 5 ты пишешь именно «официанта»:

  1. Приходит запрос: «дай заметки пользователя №1».
  2. Твой API идёт в базу данных notes.db и забирает нужные строки.
  3. API обрабатывает их: переименовывает поля, склеивает заголовок с логином.
  4. Отдаёт готовый JSON клиенту.

2.3. Из чего состоит HTTP-запрос

HTTP — язык, на котором клиент и сервер разговаривают. Каждый запрос состоит из четырёх частей:

2.4. Из чего состоит URL

http://127.0.0.1:8000/api/notes?id_user=1
│      │         │   │             │
│      │         │   │             └─ ПАРАМЕТР ЗАПРОСА (query parameter)
│      │         │   └─ ПУТЬ (path) — что за ресурс просим
│      │         └─ ПОРТ
│      └─ ХОСТ (компьютер)
└─ ПРОТОКОЛ (как передаём данные)

Параметр начинается после знака ?. Если параметров несколько, они разделяются знаком &:

/api/notes?id_user=1&limit=10

В Postman параметры удобно задавать на вкладке Params, а не вручную в строке — тогда Postman сам правильно их закодирует.

2.5. Коды ответов

Ответ всегда начинается с трёхзначного кода. По нему клиент понимает, всё ли хорошо, ещё до того, как прочитает содержимое.

КодНазваниеЧто означаетВ нашем API

400Bad RequestКлиент прислал ерунду — сервер не может это обработатьПараметр id_user не число
404Not FoundТакого адреса на сервере нетЗапрос на /api/notes/1

Правило запоминания. Первая цифра кода — «кто виноват»:
2xx — всё хорошо · 3xx — переехало, ищи в другом месте · 4xx — виноват клиент · 5xx — виноват сервер.

2.6. JSON — формат, в котором передаются данные

JSON — текстовый формат, удобный и человеку, и программе. В нём всего четыре правила:

  • объект — в фигурных скобках: {"ключ": "значение"};
  • массив (список) — в квадратных скобках: [ ... ];
  • строки — в двойных кавычках всегда;
  • между элементами — запятые, последняя запятая запрещена.

Вот как выглядит ответ нашего API:

[
  {
    "id": "00001",
    "title_user": "Конференция ИТ - user25",
    "content": "Содержимое заметки",
    "formatted_date": "03.02.2027"
  },
  {
    "id": "00002",
    "title_user": "Список задач - admin",
    "content": "Купить продукты, позвонить в банк",
    "formatted_date": "07.02.2027"
  }
]

Обрати внимание: "00001" — это строка (в кавычках), а не число. Именно этого требует задание: данные обработаны, а не отданы как есть.

2.7. Что такое Postman

Postman — программа, которая умеет отправлять HTTP-запросы и показывать ответы. Браузер тоже умеет, но умеет только GET и не умеет проверять ответы автоматически. Postman:

  • сохраняет запросы, чтобы не набирать адрес каждый раз;
  • складывает запросы в коллекцию — это просто «папка с запросами»;
  • позволяет написать тесты — код, который сам проверяет ответ и ставит «PASSED» или «FAILED»;
  • умеет прогнать всю коллекцию подряд и показать отчёт — это делает Collection Runner.

Три главные зоны окна Postman:

ЗонаГде находитсяЗачем
Боковая панельСлева CollectionsДерево коллекций, папок и запросов
Строка запросаСверху по центруМетод + адрес + кнопка Send
Область ответаСнизу по центруВкладки Body, Headers, Test Results

2.8. Что такое автотест

Автотест — это маленькая программа, которая сама проверяет ответ. В Postman тесты пишут на языке JavaScript на вкладке Scripts (в старых версиях — Tests). Скелет всегда один и тот же:

pm.test("НАЗВАНИЕ ПРОВЕРКИ", function () {
    КОД_ПРОВЕРКИ;
});

pm.test(...) означает: «выполни код внутри и, если он не выбросит ошибку, поставь этому тесту галочку PASSED, а если выбросит — крестик FAILED».

Почему это удобно. Один раз написал тест — и дальше при каждом запуске он сам проверяет, что API ничего не сломал. Это и есть «тесты, подтверждающие работоспособность решения», которые требует задание.

3. База данных: создаём notes.db простым SQL-скриптом

3.1. Что такое SQL и зачем он нам

База данных — это файл, внутри которого лежат таблицы. Таблица очень похожа на лист в Excel: у неё есть колонки (в базах их называют полями) и строки (в базах их называют записями).

SQL — язык, на котором пишут команды для базы данных. Каждая команда заканчивается точкой с запятой ;. Нам понадобятся всего три команды:

КомандаЧто делает
CREATE TABLEСоздать таблицу (объявить её колонки)
INSERT INTOДобавить в таблицу строки с данными
SELECTПрочитать данные. Эту команду за нас пишет код app.py

Никакие библиотеки устанавливать не нужно: SQL понимает сама база данных, а выполнять скрипт мы будем в программе DB Browser for SQLite.

3.2. Какие таблицы нужны нашему проекту

По заданию обязательна таблица notes (Заметки). Выглядит она так:

Имя поляТип данныхКлючСмысл

Но нужна ещё вторая таблица — users (Пользователи):

Имя поляТип данныхКлючСмысл

ПОЧЕМУ ДВЕ ТАБЛИЦЫ, ХОТЯ В ЗАДАНИИ УПОМЯНУТА ОДНА. В правилах обработки сказано: поле title_user — это «конкатенация (объединение) двух строк: title из таблицы notes и login из таблицы users». Значит, логин где-то должен храниться. Единственное подходящее место — таблица users. Без неё выполнить правило невозможно.

Две таблицы связывает поле notes.id_user: оно указывает на users.id. Например, заметка с id_user = 2 принадлежит пользователю с id = 2, то есть user25.

3.3. Даты: главное правило, из-за которого теряют баллы

ДАТА ЗАПИСЫВАЕТСЯ В БАЗУ СРАЗУ В ФОРМАТЕ ДД.ММ.ГГГГ.

Требуется "formatted_date": "03.02.2027" — день, точка, месяц, точка, год.

В нашем коде дата не преобразуется: он берёт row["created_at"] и отдаёт как есть, только под другим именем. Значит, правильный формат должен быть уже в базе.

Пиши в базе '03.02.2027' — и всё получится само.
Напишешь '2027-02-03' — клиент получит дефисы, и тест «formatted_date — дата в формате ДД.ММ.ГГГГ» станет красным.

Какие именно даты вписывать — не важно. Могут быть любые числа, любой год. Проверяется только формат: две цифры, точка, две цифры, точка, четыре цифры. Два примера допустимых значений: 03.02.2027 и 17.11.2026.

Колонка created_at имеет тип TEXT — то есть дата хранится как обычная строка. SQLite не проверяет, «настоящая» ли это дата, поэтому за формат отвечаешь ты. Это одновременно и удобно (не нужно ничего преобразовывать в коде), и опасно (можно случайно написать дату «наоборот», и никто не подскажет).

3.4. SQL-скрипт создания базы

Открой любой текстовый редактор (Блокнот тоже подойдёт), скопируй туда текст ниже и сохрани файл под именем create_db.sql в папку проекта.

Комментарии в SQL начинаются с двух дефисов --. База их не выполняет, они нужны человеку для чтения.

-- ================================================
-- Шаг 1. Удаляем старые таблицы, если они уже есть.
-- Это нужно, чтобы скрипт можно было запускать повторно
-- без ошибки «такая таблица уже существует».
-- ================================================
DROP TABLE IF EXISTS notes;
DROP TABLE IF EXISTS users;


-- ================================================
-- Шаг 2. Создаём таблицу пользователей.
-- id    — номер пользователя, первичный ключ;
-- login — логин, обязателен и не должен повторяться.
-- ================================================
CREATE TABLE users (
    id    INTEGER PRIMARY KEY,
    login TEXT NOT NULL UNIQUE
);


-- ================================================
-- Шаг 3. Создаём таблицу заметок.
-- id_user — номер пользователя из таблицы users.
-- created_at — дата. Тип TEXT: храним строкой.
-- ================================================
CREATE TABLE notes (
    id         INTEGER PRIMARY KEY,
    title      TEXT NOT NULL,
    content    TEXT,
    id_user    INTEGER NOT NULL REFERENCES users(id),
    created_at TEXT
);


-- ================================================
-- Шаг 4. Добавляем пользователей.
-- ================================================
INSERT INTO users (id, login) VALUES
    (1, 'admin'),
    (2, 'user25'),
    (3, 'ivanov'),
    (4, 'petrova');


-- ================================================
-- Шаг 5. Добавляем заметки.
-- ВНИМАНИЕ! Даты записаны сразу в формате ДД.ММ.ГГГГ.
-- Числа могут быть любые — важен только формат.
-- ================================================
INSERT INTO notes (id, title, content, id_user, created_at) VALUES
    (1, 'Конференция ИТ',     'Содержимое заметки',                   2, '03.02.2027'),
    (2, 'Список задач',       'Купить продукты, позвонить в банк',    1, '07.02.2027'),
    (3, 'Отчёт за квартал',   'Подготовить отчёт для руководителя',   3, '14.02.2027'),
    (4, 'Идеи для проекта',   'Добавить авторизацию и кэширование',   2, '21.02.2027'),
    (5, 'Встреча с командой', 'Обсудить сроки и распределение задач', 4, '28.02.2027');
ЗАЧЕМ НУЖНЫ DROP TABLE IF EXISTS. Без этих двух строк повторный запуск скрипта упал бы с ошибкой «таблица уже существует». С ними скрипт можно запускать сколько угодно раз — старые таблицы просто стираются и создаются заново. Внимание: если ты уже вносил изменения в базу, они пропадут.

3.5. Как выполнить скрипт

Вариант 1. DB Browser for SQLite (рекомендуется)
  1. Открой DB Browser for SQLite (значок на рабочем столе или в меню «Пуск»).
  2. Меню Файл → Создать базу данных (New Database).
  3. В окне сохранения выбери папку проекта (ту, где будет лежать app.py) и введи имя файла: notes.db. Нажми Сохранить.
  4. Появится окно «Редактировать определение таблицы». Нам оно не нужно — таблицы мы создадим скриптом. Нажми Отмена (Cancel).
  5. Перейди на вкладку Выполнить SQL (Execute SQL) — вторая слева.
  6. Вставь туда весь скрипт из раздела 3.4.
  7. Выдели весь текст сочетанием Ctrl+A и нажми кнопку выполнения — значок ▶ на панели сверху (или Ctrl+Return).
  8. Перейди на вкладку Структура базы данных (Database Structure): в левом списке должны появиться таблицы notes и users.
  9. Перейди на вкладку Просмотр данных (Browse Data), в выпадающем списке выбери notes — увидишь пять строк.
  10. ОБЯЗАТЕЛЬНО: нажми Записать изменения (Write Changes), иначе данные не сохранятся в файл. Иконка — дискетка на панели сверху (или Ctrl+S).
  11. Закрой DB Browser (можешь не закрывать, но перед запуском app.py лучше закрыть — иначе база может оказаться «заблокированной»).
Вариант 2. Командная строка (если есть sqlite3)

Открой терминал в папке проекта и выполни одну из команд:

sqlite3 notes.db ".read create_db.sql"

или через перенаправление ввода:

sqlite3 notes.db < create_db.sql

Проверить, что всё создалось:

sqlite3 notes.db "SELECT * FROM notes;"

Выйти из консоли базы: команда .quit.

Фрагмент 6. Команда try и сборка SQL-запроса — строки 16–24
    try:
        sql = """
            SELECT * FROM notes
            JOIN users ON users.id = notes.id_user
        """
        if id_user:
            sql += f"""WHERE notes.id_user = {int(id_user)}"""
  • try: — начало «охраняемой зоны». Всё, что идёт ниже с отступом, находится под наблюдением: если внутри что-то сломается, мы это поймаем. Подробно разберём в фрагменте 8.
  • Тройные кавычки """...""" позволяют записать текст в несколько строк — так SQL читается глазами.
  • SELECT * FROM notes — «выбери все колонки из таблицы notes». Звёздочка означает «все колонки».
  • JOIN users ON users.id = notes.id_user — соединение двух таблиц. JOIN говорит: «возьми каждую заметку и найди пользователя, чей id совпадает с notes.id_user; верни обе строки вместе». Без JOIN в ответе не было бы логина, и поле title_user собрать было бы не из чего.
  • if id_user: — если параметр передан, дописываем WHERE. Если не передан — фильтра нет, вернутся все заметки.
  • sql += ... — оператор += дописывает текст в конец переменной sql. Получится два склеенных куска: SELECT ... JOIN ... WHERE notes.id_user = 1.
  • f"""...""" — f-строка: всё, что в фигурных скобках, заменяется на значение. Здесь {int(id_user)} превращает строку "001" в число 1.
  • Значение подставляется только после проверки isdigit(). Это защита от SQL-инъекции: злоумышленник не сможет прислать 1 OR 1=1, потому что такая строка не пройдёт проверку и получит 400.
МЕЛКАЯ ДЕТАЛЬ, КОТОРАЯ РАБОТАЕТ. В обеих таблицах есть колонка с именем id, а SELECT * просит все колонки из обеих таблиц. SQLite отдаёт сначала колонки из notes, потом из users, и при чтении по имени row['id'] берётся первая — то есть notes.id. Нам нужен именно номер заметки, поэтому всё работает правильно. Запоминать это не обязательно: просто если однажды ответ начнёт путать номера — перечисли колонки явно: SELECT notes.id, notes.title, notes.content, notes.created_at, users.login.
Фрагмент 7. Выполнение запроса и обработка данных — строки 26–38
        rows = db.query(sql)

        for row in rows:

                    "title_user": f"{row['title']} - {row['login']}",
                    "content": row["content"],
                    "formatted_date": row["created_at"]

        return resp_arr

Это самое главное место работы. Здесь выполняется требование «данные не должны выдаваться в исходном виде».

  • rows = db.query(sql) — sqlite-utils выполняет запрос и возвращает набор строк.
  • resp_arr = [] — создаём пустой список. В него будем складывать готовые словари. Имя читается как «response array» — «массив для ответа».
  • for row in rows: — цикл: берём по одной строке из результата запроса. row — это одна строка таблицы.
  • resp_arr.append({...}) — добавляем в список новый словарь с четырьмя ключами. append по-английски «добавить в конец».
  • return resp_arr — список словарей автоматически превратится в JSON-массив и уедет клиенту.

Клиенту — понятное общее сообщение, разработчику — подробности в консоль. Именно так и сделано: в ответе "Ошибка подключения к базе данных", а в терминале, например, no such table: notes.
КОГДА ЭТОТ БЛОК СРАБОТАЕТ. Например: файл notes.db переименован или удалён; в базе нет таблицы notes; в параметре пришёл символ, который проходит isdigit(), но ломает int(). В любом из этих случаев вместо непонятной ошибки клиент получит аккуратный JSON с кодом 500.

4.11. Соберём всё вместе: полный код файла app.py

Теперь, когда каждая часть разобрана, вот как выглядит файл целиком. Создай в папке проекта файл app.py и вставь в него это:

import sqlite3

from fastapi import *
from fastapi.responses import JSONResponse
from sqlite_utils import Database

app = FastAPI()
db = Database(sqlite3.connect("notes.db", check_same_thread=False))

@app.get("/api/notes")
def get_notes(id_user: str | None = Query(None)):
    """Список заметок. 200 — ок, 400 — плохой параметр, 500 — сбой сервера."""
    if id_user and not id_user.isdigit():
        return JSONResponse(status_code=400, content={"error": "Параметр id_user должен быть целым числом"})

    try:
        sql = """
            SELECT * FROM notes
            JOIN users ON users.id = notes.id_user
        """
        if id_user:
            sql += f"""WHERE notes.id_user = {int(id_user)}"""
        
        rows = db.query(sql)
        
        resp_arr = []
        for row in rows:
            resp_arr.append(
                {
                    "id": f"{row['id']:05d}", 
                    "title_user": f"{row['title']} - {row['login']}", 
                    "content": row["content"],
                    "formatted_date": row["created_at"]
                }
            )
        return resp_arr

    except Exception as error:
            print("ОШИБКА при работе с базой данных:", error)
            return JSONResponse(
                status_code=500,
                content={"error": "Ошибка подключения к базе данных"},
            )

if __name__ == "__main__":
    import uvicorn

    uvicorn.run(app, host="127.0.0.1", port=8000)
ОТСТУПЫ — ЭТО ЧАСТЬ КОДА. Убедись, что файл сохранён именно с такими отступами. Если редактор «съест» пробелы в начале строк или заменит их на другие символы, Python выдаст IndentationError. Самый надёжный способ — открыть app.py в VS Code: там отступы видны как пунктирные линии, и Tab не смешивается с пробелами.

Шаг 7. Первый запрос вручную

Сделаем самый простой запрос, чтобы понять, как всё устроено.

Коллекцию ты импортировал — она уже с тестами. Но на экзамене могут попросить написать тест самостоятельно или объяснить, что он делает. Разберём всё по шагам.

Шаг 12. Где живут тесты

  2. Под адресной строкой есть ряд вкладок: Params, Authorization, Headers, Body, Scripts, Settings. В старых версиях Postman вкладка называлась Tests.

Шаг 13. Тест №1: проверяем код ответа

Шаг 14. Тест №2: проверяем скорость ответа
pm.test("Ответ пришёл быстрее 3000 мс", function () {

pm.response.responseTime — время ответа в миллисекундах, его измеряет сам Postman. .to.be.below(3000) — «должно быть меньше 3000».

Зачем это нужно. Если запрос вдруг начнёт идти 30 секунд — значит, ты написал крайне неэффективный SQL или база «тормозит». Такой тест это поймает.

Ответ сервера приходит как просто текст. Чтобы обращаться к полям по именам, текст нужно разобрать. Метод .json() делает это за тебя и возвращает готовый объект JavaScript.

Слово const означает «объявляю переменную, которую не буду переприсваивать». Она доступна во всех тестах этого запроса ниже строки объявления.

Шаг 16. Тест №4: проверяем, что пришёл массив и он не пустой

Шаг 17. Тест №5: проверяем наличие полей у каждого элемента

Шаг 18. Тест №6: id — строка из пяти цифр
pm.test("Поле id — строка из 5 цифр", function () {
    body.forEach(function (item, index) {
        pm.expect(item.id, "Заметка №" + index + ": id = " + item.id)
          .to.match(/^\d{5}$/);
    });
});

Регулярное выражение — это шаблон, описывающий «как должна выглядеть строка». Записано между косыми чертами: /^\d{5}$/.

СимволЧто означает
/ /Границы регулярного выражения
^«начало строки»
\dлюбая цифра от 0 до 9
{5}«ровно пять раз подряд»
$«конец строки»
Проверим на примерах.
"00001" — 5 цифр, ничего лишнего → подходит.
"1" — одна цифра, мало → не подходит.
"0001a" — последний символ не цифра → не подходит.
"000011" — шесть цифр, а $ требует, чтобы после пятой был конец строки → не подходит.
Без ^ и $ выражение \d{5} пропустило бы «000011», потому что нашлись пять цифр подряд. Знаки «начало» и «конец» обязательны.
Шаг 19. Тест №7: formatted_date в формате ДД.ММ.ГГГГ
pm.test("formatted_date — дата в формате ДД.ММ.ГГГГ", function () {
    body.forEach(function (item, index) {
        pm.expect(item.formatted_date, "Заметка №" + index + ": " + item.formatted_date)
          .to.match(/^\d{2}\.\d{2}\.\d{4}$/);
    });
});

Шаблон читается так:

Кусок шаблонаЧто требует
^начало строки
\d{2}две цифры — день
\.точка. Обратный слэш обязателен: без него точка в шаблоне означает «любой символ», а нам нужна именно точка
\d{2}две цифры — месяц
\.снова точка
\d{4}четыре цифры — год
$конец строки — ничего лишнего после года
ЭТОТ ТЕСТ ПРОВЕРЯЕТ ИМЕННО ФОРМАТ, А НЕ КОНКРЕТНУЮ ДАТУ. Ему всё равно, какое число в базе. Он требует только одно: две цифры, точка, две цифры, точка, четыре цифры. Если тест красный — значит, в базе дата записана с дефисами или с временем. Иди в DB Browser и исправь (раздел 3.7).
Шаг 20. Тест №8: проверяем, что данные обработаны
pm.test("Данные отданы в обработанном виде, а не как в базе", function () {
    const raw = pm.response.text();
    pm.expect(raw).to.not.include("created_at");
    pm.expect(raw).to.not.include('"login":');
    pm.expect(raw).to.not.include('"id_user":');
    pm.expect(raw).to.not.include('"title":');
});

Это самый важный тест модуля 5, потому что он проверяет главное требование задания.

  • pm.response.text() — берём ответ как есть, сырым текстом, не разбирая JSON. Так мы видим точные имена полей;
  • .to.not.include("created_at") — «в ответе НЕ должно быть подстроки created_at». В базе колонка так называется, в ответе — уже formatted_date;
  • .to.not.include('"login":') — ищем именно "login": вместе с кавычками и двоеточием, то есть как имя поля. Логин как значение внутри title_user остаётся — это не ошибка;
  • обратные кавычки и апострофы: если внутри строки есть кавычка ", строку в JavaScript удобнее писать в одинарных кавычках '...'.

Шаг 22. Тест №10: валидность JSON
pm.test("Тело ответа успешно разбирается как JSON", function () {

});

Логика предельно простая: JSON.parse — стандартная функция JavaScript, которая разбирает текст в объект. Если текст сломан, функция выбрасывает ошибку — и pm.test автоматически ставит тесту FAILED. Если разобралось — тест зелёный.

ПОЧЕМУ ЭТО ЧЕСТНАЯ ПРОВЕРКА. Проверка валидности JSON выполняется в каждом из четырёх запросов. Так и должно быть: клиент должен уметь разобрать ответ в любом случае — и когда всё хорошо, и когда пришла ошибка.
